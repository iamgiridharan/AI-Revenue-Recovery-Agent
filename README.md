# AI Revenue Recovery Agent

An AI-powered system that detects failed payments, predicts recovery probability, recommends recovery actions, validates through a deterministic policy engine, and executes controlled payment recovery via Razorpay Test Mode.

**Status:** MVP Complete — Recovery Pipeline Verified ✅  
**Payment Integration:** Razorpay Test Mode ONLY  
**Latest Verification:** 390 automated tests passing; simulated recovery outcomes and the controlled Test Mode recovery flow (locally executed against a stub provider) confirmed

---

## Problem Statement

Businesses lose significant revenue from failed subscription and recurring payments. Manual recovery is slow, inconsistent, and doesn't scale. Existing solutions lack intelligent prioritization and controlled automation.

## Solution

An end-to-end AI agent that:
1. Detects failed payments and creates revenue risk cases
2. ML model predicts recovery probability for each case
3. AI agent diagnoses the failure and recommends recovery actions
4. Deterministic Policy Engine validates every recommendation before execution
5. Controlled recovery tools execute approved actions via Razorpay Test Mode
6. Webhook processing captures payment outcomes
7. Complete audit trail records every decision
8. Merchant dashboard displays real-time metrics

## Key Differentiators

1. **AI recommends but cannot execute** — The LLM/agent proposes recovery actions but never directly executes financial operations.
2. **Deterministic policy engine** — Every recovery action is validated by a deterministic rule engine before execution. No action bypasses policy.
3. **ML + AI + Policy combination** — Machine learning predicts recovery probability, the AI agent diagnoses failures, and the policy engine authorizes actions — three independent controls.
4. **Trusted data sources** — Financial amounts and transaction data always come from the database, never from the LLM.
5. **Safe escalation** — Low-confidence or high-risk cases are escalated to human review rather than attempted automatically.
6. **Complete audit trail** — Every decision (ML prediction, AI recommendation, policy check, recovery action) is recorded with timestamps and context.
7. **Simulation engine** — The complete pipeline can be demonstrated using explicitly labeled synthetic/simulated data, without requiring real payment credentials.

## Data Flow

### Complete Recovery Flow

```
1. Payment fails (webhook/manual)
2. Revenue Risk Case created
3. ML Model predicts recovery probability
4. AI Agent diagnoses failure, recommends action
5. Policy Engine validates recommendation
   → APPROVED: proceed to step 6
   → BLOCKED: stop, audit, notify
   → ESCALATED: human review required
6. Recovery Service executes approved action
7. Razorpay Test Mode processes payment
8. Webhook receives payment outcome
9. Case status updated
10. Audit event recorded
11. Dashboard metrics refresh
```

### Simulation Flow

The simulation engine runs synthetic transactions through the complete pipeline without requiring real payment credentials:

```
1. Generate synthetic customer + transaction data
2. Create Customer, Transaction, and RevenueRiskCase in DB
3. ML Model predicts recovery probability
4. AI diagnosis generated (deterministic mock, no LLM call)
5. Policy Engine evaluates recommended action
   → APPROVED: execute simulated recovery
   → BLOCKED/ESCALATED: record outcome, update case
6. Simulated payment outcome (success/failure based on configured rates)
7. Case status updated (RECOVERED / OPEN / ESCALATED)
8. Audit events recorded at every step
```

**All simulation output is labeled `SIMULATED`.** It is not real customer revenue.

## Deterministic Policy Engine

The Policy Engine validates every AI recommendation before execution.

### Policy Rules

| Rule | Default | Description |
|------|---------|-------------|
| MAX_RETRIES | 2 | Maximum retry attempts per case |
| MAX_REMINDERS | 2 | Maximum payment reminders per case |
| MAX_RECOVERY_ATTEMPTS | 3 | Maximum total recovery actions |
| AUTONOMOUS_AMOUNT_LIMIT | ₹10,000 | Maximum amount for autonomous action |
| MINIMUM_AI_CONFIDENCE | 0.3 | Minimum confidence required |
| MINIMUM_RECOVERY_PROBABILITY | 0.2 | Minimum recovery probability |
| CASE_LIFETIME_DAYS | 7 | Maximum case age before expiry |

### Policy Validation

The system includes sanity validation to prevent configurations that would make recovery impossible:
- `autonomous_amount_limit` must be ≥ 100
- `minimum_ai_confidence` must be ≤ 0.95
- `minimum_recovery_probability` must be ≤ 0.95

Invalid configurations are **rejected by the API** (`PUT /api/policies` returns a validation
error). Runtime reads never rewrite a stored policy: values outside these ranges are logged
as a warning and left exactly as configured, so operator settings (including a deliberately
low autonomous amount limit) are preserved.

### Decisions

- **APPROVED:** All checks passed, action allowed
- **BLOCKED:** Critical check failed, action prevented
- **ESCALATED:** A configured limit was exceeded (amount, AI confidence or recovery
  probability) and human review is required. The case is moved to the `ESCALATED` status
  and a `CASE_ESCALATED` audit event is recorded, so escalations are visible to the
  dashboard and to operators. Escalation is driven by those limits alone — there is no
  separate escalation threshold setting; a low `minimum_ai_confidence` never forces
  escalation, it only stops the autonomous flow at the point it would otherwise act.

## Value-Aware Recovery Scoring (Estimates)

Recovery candidates can be scored by estimated value so that a human (or the agent)
can see what a recovery attempt is worth. The calculation is deterministic:

```
expected gross recovery = payment amount × probability of verified recovery
expected net recovery   = expected gross recovery − intervention cost
utility score          = expected net recovery − configured penalties
```

Every figure is returned separately (`expected_gross_recovery`, `intervention_cost`,
`expected_net_recovery`, `utility_score`, `penalties`) with its provenance, and is
labelled `ESTIMATE`. Estimates are never written to `recovered_amount`, which is only
set by a verified payment webhook.

### What the probability is (and is not)

`recovery_probability` is a **case-level** model output: the RandomForest predicts
whether a failed payment ends up recovered (target `recovered`) from features known at
failure time. It is **not** an action-specific probability — the model has no notion of
"recovery probability *given* a payment link vs. a reminder". The same probability is
therefore applied to every candidate action, so the estimate improves the *level* of the
value and cross-case comparison, but it cannot discriminate between actions for one case.
Ranking differences within a case come from intervention cost and eligibility only.
No per-action probability is invented; callers may inject action-specific probabilities
explicitly, in which case the response marks them `caller_supplied` and flags the estimate
as action-specific.

Measured quality of the case-level probability (from
`ml/saved_models/evaluation_summary_v1.json`, held-out synthetic split) is reported with
every assessment: **ROC-AUC 0.668, precision 0.328, recall 0.186, base rate 0.170**.

### Intervention costs

No intervention costs are measured anywhere in this system. A cost is used only when a
deployment configures one (`INTERVENTION_COSTS`) — it is never assumed. When no cost is
available, `expected_net_recovery` is reported as **not computed** rather than silently
treated as zero. Penalties are never folded into the net-recovery formula: they are
itemized separately and applied only to the utility score, which is explicitly not a
monetary figure.

### Eligibility and safety

Value scoring **ranks eligible candidate actions and never authorizes or executes anything**:

- The Policy Engine remains the sole authorization authority; the only policy use here is a
  non-persisting pre-check (`persist=False`) that writes no decision or audit row.
- Candidates blocked or escalated by policy, terminal cases (`RECOVERED`, `CLOSED`), already
  recovered payments, and non-executable actions are excluded from the ranking and listed
  with the reason instead.
- The response always states `authorization: {required: true, authority: "policy_engine"}`.
- Retry limits, approval thresholds, monetary limits, webhook behaviour and provider
  integrations are unchanged by this feature.

### Where to see it

- `GET /api/cases/{case_id}/value` — the full assessment (formula, inputs, provenance,
  gross/cost/net/utility, ranked and excluded candidates, assumptions, limitations).
- `GET /api/cases/{case_id}/detail` — the same assessment under `value_assessment`.
- Case detail page — an “Estimated Recovery Value” panel showing the formula, inputs and
  assumptions, with estimates visually separated from actual recovered revenue.

## Razorpay Integration

- **Mode:** Test Mode ONLY (never Live Mode)
- **Payment Links:** Created via Razorpay API
- **Webhook Handling:** Verifies signature (fails closed when no secret is configured), prevents duplicates
- **Mock Mode:** Falls back to mock behavior when credentials are not configured

> **Note:** Without Razorpay Test Mode credentials configured, the system operates in mock/simulated mode. No real payment links are created. The simulation pipeline demonstrates recovery outcomes without requiring Razorpay credentials.

### Controlled Recovery Execution

`POST /api/cases/{case_id}/recovery` executes a case's **recorded AI recommendation**
and, for `CREATE_PAYMENT_LINK` / `RETRY`, creates the payment link. The request body
only selects the action (`{"action_type": "RETRY", "reason": "..."}`, both optional):

- The **amount** always comes from the database transaction record, and the
  **confidence / recovery probability** always come from the recorded diagnosis.
  A caller cannot supply either, so it cannot step over `MINIMUM_AI_CONFIDENCE` or
  choose what will be charged.
- The **Policy Engine authorizes the action before any provider call**. A `BLOCKED` or
  `ESCALATED` decision returns **403** (with the full decision) and creates nothing.
  `RECOVERED` / `CLOSED` cases return **409** — a settled case is never acted on again.
- The link carries the case on **both** `reference_id` and `notes.case_id`, so a webhook
  can always be traced back to the right case.
- The response and the audit trail state how the link was created:
  `execution_mode: "RAZORPAY_TEST_MODE"` (a real Test Mode object) or
  `execution_mode: "MOCK"` (no provider call was made and the placeholder link —
  `https://mock.invalid/...` — cannot be paid). Mock execution is never labelled or
  recorded as a payment.
- No secrets are returned; the API returns only the link, its id, amount, mode,
  provider status and the policy decision.

The case is only marked `RECOVERED` by a verified payment webhook.

### Webhook Events Handled

- `payment.captured` / `payment_link.paid` → **settles** the case (status `RECOVERED`,
  `recovered_amount` booked) — only when the captured amount equals the amount due
- `payment.failed` / `payment_link.expired` → failure: the case is reopened for the next
  attempt, unless it is already settled (then the event is recorded and ignored)
- `payment.authorized` → recorded, **not** settled: an authorization is not a capture,
  so it must not book revenue that may never arrive
- Unknown events → Logged and acknowledged

### Webhook Safety

- **Signature:** HMAC-SHA256 over the raw body, compared with the raw body, failing
  closed. With no `RAZORPAY_WEBHOOK_SECRET` configured every delivery is rejected (401)
  rather than trusted.
- **Idempotency (durable):** every handled delivery is recorded by its provider event id
  in the `webhook_events` table. A redelivery — also after a restart or on another
  worker, where an in-memory cache would forget — is answered as a duplicate and applies
  nothing twice, so recovered revenue is never double-counted.
- **Ordering:** a delivery is recorded only *after* it has been handled, so a failed
  delivery stays retryable; late or duplicate events for a settled case are recorded and
  ignored instead of reopening or corrupting it.
- **Amount:** a capture that is non-positive or different from the amount due is refused
  with a `PAYMENT_SUCCESS_AMOUNT_UNVERIFIED` / `PAYMENT_SUCCESS_AMOUNT_MISMATCH` audit
  event, and the case is left for manual reconciliation.

### Configuring Razorpay Test Mode

Credentials are read from `backend/.env` (already ignored by Git — see `.gitignore`);
never commit them and never paste them into the frontend.

| Variable | Where it comes from |
|----------|---------------------|
| `RAZORPAY_KEY_ID` | Razorpay Dashboard → Account & Settings → **API Keys** → *Generate Test Key* (Test Mode toggle on). Starts with `rzp_test_` |
| `RAZORPAY_KEY_SECRET` | Shown once, next to the Test Key ID. Copy it immediately |
| `RAZORPAY_WEBHOOK_SECRET` | Razorpay Dashboard → Account & Settings → **Webhooks** → *Add New Webhook*: URL = `https://<your-public-host>/api/webhooks/razorpay`, secret = a value you choose. Subscribe to `payment.captured`, `payment_link.paid`, `payment.failed`, `payment_link.expired` |

Razorpay only delivers webhooks to a public HTTPS URL. For a demonstration either

- deploy the backend (Render is already configured in `render.yaml`) and point the
  webhook at `https://<service>.onrender.com/api/webhooks/razorpay`, or
- expose the local API through an HTTPS tunnel, e.g.
  `ngrok http 8000` and use the `https://<id>.ngrok-free.app/api/webhooks/razorpay`
  URL it prints. The tunnel URL changes when it restarts, so update the webhook URL
  in the dashboard when it does.

### One Test Mode Payment, End to End

1. Put the three values above in `backend/.env`, then restart the backend so the
   settings are re-read.
2. Confirm they are loaded: `GET /api/health` (and check the startup log line
   `Razorpay client initialized successfully (Test Mode)`).
3. Start the public endpoint (deploy, or `ngrok http 8000`) and set that URL as the
   webhook in the Razorpay dashboard, with the same secret as
   `RAZORPAY_WEBHOOK_SECRET`.
4. Create or pick a case and diagnose it: `POST /api/agent/diagnose` with
   `{"case_id": "<CASE-ID>"}` (or open the case page and use *Execute recovery
   action*).
5. Execute the recommendation: `POST /api/cases/<CASE-ID>/recovery` with `{}`, or the
   button on the case detail page. The response must say
   `"execution_mode": "RAZORPAY_TEST_MODE"`; if it says `MOCK`, the credentials are not
   being picked up and no real link exists.
6. Open the returned `payment_link` and pay with a Razorpay **test instrument** (for
   example a test card, or UPI `success@razorpay`). No real money moves.
7. Watch the case: within a few seconds the webhook settles it — status `RECOVERED`,
   `recovered_amount` equal to the case amount, a `PAYMENT_SUCCESS` audit event from
   actor `webhook`, and one `webhook_events` row for the delivery.
8. Verify the single booking: re-send the same webhook (Razorpay's *Resend* button, or
   replay the delivery) and confirm the response says `Duplicate event ignored` and the
   case's `recovered_amount` is unchanged.

Until steps 1–3 are done the flow can only be exercised in `MOCK` mode (or by
simulating a signed delivery locally); the real provider round trip is unverified.

| Outcome | Typical Range | Description |

> **Note:** Recovery rates vary based on transaction characteristics, ML predictions, and policy configuration. The simulation is deterministic given the same random seed.

## Environment Variables

| Variable | Required | Description |
|----------|----------|-------------|
| `DATABASE_URL` | Yes | PostgreSQL connection string |
| `RAZORPAY_KEY_ID` | No | Razorpay Test Mode key |
| `RAZORPAY_KEY_SECRET` | No | Razorpay Test Mode secret |
| `RAZORPAY_WEBHOOK_SECRET` | Yes (for webhooks) | Razorpay webhook secret. Webhook signature verification fails closed without it |
| `LLM_API_KEY` | No | LLM API key (mock used if empty) |
| `INTERVENTION_COSTS` | No | JSON map of action → intervention cost in INR for value scoring, e.g. `{"RETRY": 3.0}`. Empty means no cost is available, so expected net recovery is not computed |
| `UTILITY_PENALTIES` | No | JSON map of action → contact/operational penalty in INR applied only to the utility score |
| `DEBUG` | No | Enable debug mode |
| `CORS_ORIGINS` | No | Allowed CORS origins |

## Deployment

### Frontend (Vercel)

1. Push to GitHub
2. Connect repository to Vercel
3. Set build command: `npm run build`
4. Set output directory: `dist`
5. Configure API proxy rewrite to backend URL

### Backend (Render/Railway)

1. Push to GitHub
2. Create new Web Service
3. Set build command: `pip install -r backend/requirements.txt`
4. Set start command: `cd backend && uvicorn app.main:app --host 0.0.0.0 --port $PORT`
5. Add environment variables (DATABASE_URL, Razorpay keys, etc.)
6. Health check path: `/api/health`

### Database (Cloud PostgreSQL)

1. Create PostgreSQL instance (Render, Supabase, Neon, etc.)
2. Copy connection string to `DATABASE_URL` env var
3. Run Alembic migrations: `cd backend && alembic upgrade head`

### Post-Deployment

1. Verify health endpoint: `GET /api/health`
2. Run simulation: `POST /api/simulation/run`
3. Check dashboard metrics
4. Configure Razorpay webhook URL: `https://your-backend.onrender.com/api/webhooks/razorpay`

## Demo Instructions

### Prerequisites
- Backend running on port 8000
- Frontend running on port 5173
- Database connected

### Demo Flow

1. **Open Dashboard** — Show overview metrics (empty initially)
2. **Run Simulation** — Execute 100-transaction simulation via Swagger (`POST /api/simulation/run` with `{"num_transactions": 100, "seed": 42}`)
3. **Refresh Dashboard** — Show populated metrics and charts:
   - Total cases and revenue at risk
   - Revenue recovered and recovery rate
   - Recovered, open, and escalated case counts
   - Status, priority, and action breakdown charts
   - Daily cases and recovery trends
4. **View Cases** — Browse simulated revenue risk cases, filter by status
5. **Case Detail** — Open a RECOVERED case to show the complete timeline:
   - Payment Failed → Risk Detected → AI Analysis → Recovery Recommended → Policy Approved → Action Executed → Payment Successful
6. **Audit Trail** — Show audit events for a case via the case detail page or `GET /api/audit`
7. **Policy Settings** — Show and modify policy configuration (`GET /api/policies`)
8. **Agent Monitor** — Show audit events from simulation

### Demonstrating Key Scenarios

**Successful Recovery:**
- Filter cases by status "RECOVERED"
- Show full timeline: failure → ML → AI → Policy → Recovery → Success
- Point out the recovered amount and audit trail

**Policy Block:**
- Show cases with BLOCKED_BY_POLICY recovery actions
- Explain that the policy engine prevented action due to confidence limits or amount thresholds

**Escalation:**
- Show cases with low confidence or high amounts
- Verify escalation to human review
- Show audit trail with ESCALATED decisions

**Policy Configuration:**
- Update policy settings via `PUT /api/policies`
- Show validation errors for extreme values (e.g., `{"minimum_ai_confidence": 1.0}`)

## Security Considerations

- ✅ No secrets in frontend code
- ✅ `.env` excluded from Git
- ✅ `.env.example` contains only placeholders
- ✅ Razorpay Test Mode only (never Live Mode)
- ✅ Razorpay secret keys only on backend
- ✅ Webhook signature verification enabled (fails closed: unsigned webhooks are rejected with 401)
- ✅ Duplicate webhook protection (durable: recorded in the database, survives restarts)
- ✅ Only captured payments with the exact amount due settle a case
- ✅ Policy limits enforced on all actions
- ✅ Recovery execution requires a recorded AI diagnosis and policy authorization
- ✅ Mock executions are labelled MOCK and never presented as a payment
- ✅ LLM cannot bypass Policy Engine
- ✅ Amounts come from trusted database, not LLM
- ✅ Frontend cannot execute payment operations
- ✅ Simulation labeled as SIMULATED
- ✅ Policy sanity validation prevents impossible configurations

## Limitations

1. **LLM is mocked** — Uses deterministic rules instead of real LLM API
2. **No real provider round trip has been executed yet** — the controlled recovery flow
   and webhook handling are implemented and verified with a stubbed provider (and a
   locally signed webhook); creating a real Test Mode payment link and receiving a real
   Razorpay webhook delivery requires Test Mode credentials and a public HTTPS URL
3. **Recovery execution has no authentication** — consistent with the rest of this MVP
   (single tenant, no user accounts), but `POST /api/cases/{case_id}/recovery` is a
   mutation endpoint: in a deployed demonstration it should sit behind authentication,
   and it must never run with Live Mode credentials
4. **Single-tenant** — No merchant authentication/authorization
5. **No real-time updates** — Dashboard requires manual refresh
6. **SQLite for tests** — Production uses PostgreSQL
7. **No action-specific recovery probabilities** — the ML model predicts a case-level
   probability of recovery, so value scoring cannot rank actions by likelihood; with one
   shared probability and no costs configured, ranking is driven by cost and eligibility
8. **No measured intervention costs** — net recovery is only computed when a deployment
   configures `INTERVENTION_COSTS`; otherwise it is reported as not computed
