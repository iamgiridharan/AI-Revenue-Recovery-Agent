# AI Revenue Recovery Agent

An AI-powered system that detects failed payments, predicts recovery probability, recommends recovery actions, validates through a deterministic policy engine, and executes controlled payment recovery via Razorpay Test Mode.

**Status:** MVP Complete — Recovery Pipeline Verified ✅  
**Payment Integration:** Razorpay Test Mode ONLY  
**Latest Verification:** 529 automated tests passing; simulated recovery outcomes, the controlled Test Mode recovery flow (locally executed against a stub provider), the human-review flow, MOCK-vs-Test-Mode reporting, reminder delivery truthfulness (NOT_SENT / SIMULATED), deterministic diagnosis provenance, and separated verified / simulated / predicted money figures confirmed

---

## Problem Statement

Businesses lose significant revenue from failed subscription and recurring payments. Manual recovery is slow, inconsistent, and doesn't scale. Existing solutions lack intelligent prioritization and controlled automation.

## Solution

An end-to-end AI agent that:
1. Detects failed payments and creates revenue risk cases
2. ML model predicts recovery probability for each case
3. AI agent diagnoses the failure and recommends recovery actions
4. Deterministic Policy Engine validates every recommendation before execution
5. Controlled recovery tools execute approved actions via Razorpay Test Mode
6. Webhook processing captures payment outcomes
7. Complete audit trail records every decision
8. Merchant dashboard displays real-time metrics

## Key Differentiators

1. **AI recommends but cannot execute** — The LLM/agent proposes recovery actions but never directly executes financial operations.
2. **Deterministic policy engine** — Every recovery action is validated by a deterministic rule engine before execution. No action bypasses policy.
3. **ML + AI + Policy combination** — Machine learning predicts recovery probability, the AI agent diagnoses failures, and the policy engine authorizes actions — three independent controls.
4. **Trusted data sources** — Financial amounts and transaction data always come from the database, never from the LLM.
5. **Safe escalation** — Low-confidence or high-risk cases are escalated to human review rather than attempted automatically.
6. **Complete audit trail** — Every decision (ML prediction, AI recommendation, policy check, recovery action) is recorded with timestamps and context.
7. **Simulation engine** — The complete pipeline can be demonstrated using explicitly labeled synthetic/simulated data, without requiring real payment credentials.

## Data Flow

### Complete Recovery Flow

```
1. Payment fails (webhook/manual)
2. Revenue Risk Case created
3. ML Model predicts recovery probability
4. Diagnosis engine classifies the stored failure reason and recommends action
   (deterministic rules, no LLM in this build — see *Diagnosis provenance*)
5. Policy Engine validates recommendation
   → APPROVED: proceed to step 6
   → BLOCKED: stop, audit, notify
   → ESCALATED: human review required
6. Recovery Service executes approved action
7. Razorpay Test Mode processes payment
8. Webhook receives payment outcome
9. Case status updated
10. Audit event recorded
11. Dashboard metrics refresh
```

### Simulation Flow

The simulation engine runs synthetic transactions through the complete pipeline without requiring real payment credentials:

```
1. Generate synthetic customer + transaction data
2. Create Customer, Transaction, and RevenueRiskCase in DB
3. ML Model predicts recovery probability
4. AI diagnosis generated (deterministic mock, no LLM call)
5. Policy Engine evaluates recommended action
   → APPROVED: execute simulated recovery
   → BLOCKED/ESCALATED: record outcome, update case
6. Simulated payment outcome (success/failure based on configured rates)
7. Case status updated (RECOVERED / OPEN / ESCALATED)
8. Audit events recorded at every step
```

**All simulation output is labeled `SIMULATED`.** It is not real customer revenue.

## AI Agent Architecture

- **Structured Output:** Pydantic-validated recommendations
- **Controlled Actions:** 7 possible recovery actions (enum-controlled)
- **Tool Authorization:** Agent recommends, Policy Engine authorizes
- **Fallback:** Safe escalation when LLM is unavailable or output is invalid

### Recovery Actions

| Action | Description |
|--------|-------------|
| NO_ACTION | No recovery action needed |
| RETRY | Retry the failed payment |
| CREATE_PAYMENT_LINK | Create Razorpay payment link |
| SEND_PAYMENT_REMINDER | Reminder to customer — **unavailable in this build** (no email/SMS provider): never recommended or authorized, simulation-only; see below |
| WAIT_AND_RETRY | Wait and retry later |
| ESCALATE_TO_HUMAN | Escalate to human review |
| MARK_UNRECOVERABLE | Mark as unrecoverable |

### Action availability: recommend only what can be executed

`backend/app/services/action_availability.py` is the single catalog of what this
deployment can carry out. The value ranking, the Policy Engine, the recovery
executor, the agent tools, the API and the UI all read it, so a recommendation and
an authorization cannot disagree.

| State | Meaning | Recommended / authorized? |
|-------|---------|---------------------------|
| `EXECUTABLE` | The action has working integration here (`CREATE_PAYMENT_LINK`, `RETRY`) | Yes |
| `SIMULATED_ONLY` | Supported, but the integration it needs is missing, so only the simulation pipeline can carry it out (`SEND_PAYMENT_REMINDER`) | No — excluded from ranking, refused by policy |
| `UNAVAILABLE` | No executor at all (decision actions such as `NO_ACTION`, `WAIT_AND_RETRY`, `ESCALATE_TO_HUMAN`, `MARK_UNRECOVERABLE`) or an unknown action type | No |

A reminder needs an email/SMS provider, which is not integrated, so it is
`SIMULATED_ONLY`: `POST /api/cases/{id}/recovery` answers `409` with
`code: ACTION_UNAVAILABLE`, `availability` naming the missing
`reminder_delivery_provider`, and **no attempt is recorded at all** — the case is
untouched and no reminder or attempt budget is spent. The value ranking lists it
under `unavailable_actions` instead of `candidates`, and the case page disables the
pick and shows the reason. A named reviewer cannot override it either: approving a
reminder is refused by the Policy Engine (`ACTION_AVAILABILITY`), so the case stays
`ESCALATED`.

The reminder functionality itself is preserved and stays extensible: implement
delivery and return the channel from `reminder_delivery_channel()`, and the reminder
becomes `EXECUTABLE` everywhere at once. Behind the authorization gate the executor
still records the truth instead of a fabricated success:

| State | Meaning | Consumes a reminder / attempt budget? |
|-------|---------|---------------------------------------|
| `NOT_SENT` | Reached the executor with no delivery channel; nothing left the system | **No** |
| `SIMULATED` | The case is simulation data; nothing left the system | Yes (simulation flow) |
| `DELIVERED` | A provider confirmed delivery — requires a real channel, so it is not produced in this build | Yes |

If an execution ever does reach that path, the API answers `503` with
`code: REMINDER_NOT_DELIVERED`, `delivery_status: NOT_SENT` and `delivered: false`;
no `api_reference` is invented, the audit event records `ACTION_FAILED` /
`REMINDER_NOT_SENT`, and the dashboard's “successful actions” count does not move.
The agent-side helpers (`agent_tools.send_payment_reminder`, `retry_payment`) refuse
the same way, and `check_recovery_status` reads the real case status from the
database.

### Diagnosis provenance: no language model runs

`POST /api/agent/diagnose` records a diagnosis produced by a deterministic rule
engine (`backend/app/services/agent_service.py`): the failure cause comes from the
stored `failure_reason`, the recovery probability is the ML model's stored
case-level value, and the confidence is a documented rule score. The response says
so explicitly:

```json
{
  "model_used": "deterministic-rules-v1",
  "diagnosis_source": "DETERMINISTIC_RULES",
  "llm_used": false,
  "confidence_source": "deterministic_rule_score",
  "recovery_probability_source": "ml_model_case_level"
}
```

The same provenance is stored in the `DIAGNOSIS_COMPLETED` audit event and returned
as `diagnosis_provenance` on `GET /api/cases/{case_id}/detail`, so the UI labels
rule output as rule output. The Policy Engine is given the validated ML probability
stored on the case — never a number the diagnosis engine claims — and a case with
no usable ML probability is escalated to a human instead of being authorized on an
invented value. A real LLM integration replaces `call_llm` and these constants
together.

## Deterministic Policy Engine

The Policy Engine validates every AI recommendation before execution.

### Policy Rules

| Rule | Default | Description |
|------|---------|-------------|
| MAX_RETRIES | 2 | Maximum retry attempts per case |
| MAX_REMINDERS | 2 | Maximum payment reminders per case |
| MAX_RECOVERY_ATTEMPTS | 3 | Maximum total recovery actions |
| AUTONOMOUS_AMOUNT_LIMIT | ₹10,000 | Maximum amount for autonomous action |
| MINIMUM_AI_CONFIDENCE | 0.3 | Minimum confidence required |
| MINIMUM_RECOVERY_PROBABILITY | 0.2 | Minimum recovery probability |
| CASE_LIFETIME_DAYS | 7 | Maximum case age before expiry |

### Policy Validation

The system includes sanity validation to prevent configurations that are out of range:
- `autonomous_amount_limit` must be between 100 and 100,000
- `minimum_ai_confidence` must be between 0.1 and 1.0
- `minimum_recovery_probability` must be between 0.05 and 1.0
- `case_lifetime_days` must be between 1 and 90

A threshold of exactly `1.0` is valid and means **no autonomous action**: every
recommendation is escalated to human review. This is the strictest safe setting, and the
Policy Settings UI offers it (0.1 - 1.0).

Invalid configurations are **rejected by the API** (`PUT /api/policies` returns a validation
error). Runtime reads never rewrite a stored policy: values outside these ranges are logged
as a warning and left exactly as configured, so operator settings (including a deliberately
low autonomous amount limit) are preserved.

### Decisions

- **APPROVED:** All checks passed, action allowed
- **BLOCKED:** Critical check failed, action prevented
- **ESCALATED:** A configured limit was exceeded (amount, AI confidence or recovery
  probability) and human review is required. The case is moved to the `ESCALATED` status
  and a `CASE_ESCALATED` audit event is recorded, so escalations are visible to the
  dashboard and to operators. Escalation is driven by those limits alone — there is no
  separate escalation threshold setting; a low `minimum_ai_confidence` never forces
  escalation, it only stops the autonomous flow at the point it would otherwise act.

## Value-Aware Recovery Scoring (Estimates)

Recovery candidates can be scored by estimated value so that a human (or the agent)
can see what a recovery attempt is worth. The calculation is deterministic:

```
expected gross recovery = payment amount × probability of verified recovery
expected net recovery   = expected gross recovery − intervention cost
utility score          = expected net recovery − configured penalties
```

Every figure is returned separately (`expected_gross_recovery`, `intervention_cost`,
`expected_net_recovery`, `utility_score`, `penalties`) with its provenance, and is
labelled `ESTIMATE`. Estimates are never written to `recovered_amount`, which is only
set by a verified payment webhook.

### What the probability is (and is not)

`recovery_probability` is a **case-level** model output: the RandomForest predicts
whether a failed payment ends up recovered (target `recovered`) from features known at
failure time. It is **not** an action-specific probability — the model has no notion of
"recovery probability *given* a payment link vs. a reminder". The same probability is
therefore applied to every candidate action, so the estimate improves the *level* of the
value and cross-case comparison, but it cannot discriminate between actions for one case.
Ranking differences within a case come from intervention cost and eligibility only.
No per-action probability is invented; callers may inject action-specific probabilities
explicitly, in which case the response marks them `caller_supplied` and flags the estimate
as action-specific.

Measured quality of the case-level probability (from
`ml/saved_models/evaluation_summary_v1.json`, held-out synthetic split) is reported with
every assessment: **ROC-AUC 0.668, precision 0.328, recall 0.186, base rate 0.170**.

### Intervention costs

No intervention costs are measured anywhere in this system. A cost is used only when a
deployment configures one (`INTERVENTION_COSTS`) — it is never assumed. When no cost is
available, `expected_net_recovery` is reported as **not computed** rather than silently
treated as zero. Penalties are never folded into the net-recovery formula: they are
itemized separately and applied only to the utility score, which is explicitly not a
monetary figure.

### Eligibility and safety

Value scoring **ranks eligible candidate actions and never authorizes or executes anything**:

- The Policy Engine remains the sole authorization authority; the only policy use here is a
  non-persisting pre-check (`persist=False`) that writes no decision or audit row.
- Candidates blocked or escalated by policy, terminal cases (`RECOVERED`, `CLOSED`), and already
  recovered payments are excluded from the ranking and listed with the reason instead.
- Actions this deployment cannot execute are never ranked: they are listed separately under
  `unavailable_actions` with the missing integration named (`SEND_PAYMENT_REMINDER` needs an
  email/SMS provider), from the same catalog the Policy Engine authorizes against.
- The response always states `authorization: {required: true, authority: "policy_engine"}`.
- Retry limits, approval thresholds, monetary limits, webhook behaviour and provider
  integrations are unchanged by this feature.

### Where to see it

- `GET /api/cases/{case_id}/value` — the full assessment (formula, inputs, provenance,
  gross/cost/net/utility, ranked and excluded candidates, assumptions, limitations).
- `GET /api/cases/{case_id}/detail` — the same assessment under `value_assessment`, plus
  `action_availability` (the catalog, so the UI can disable an unavailable action with its reason).
- Case detail page — an “Estimated Recovery Value” panel showing the formula, inputs and
  assumptions, with estimates visually separated from actual recovered revenue.

## Razorpay Integration

- **Mode:** Test Mode ONLY (never Live Mode)
- **Payment Links:** Created via Razorpay API
- **Webhook Handling:** Verifies signature (fails closed when no secret is configured), prevents duplicates
- **Mock Mode:** Falls back to mock behavior when credentials are not configured

> **Note:** Without Razorpay Test Mode credentials configured, the system operates in mock/simulated mode. No real payment links are created. The simulation pipeline demonstrates recovery outcomes without requiring Razorpay credentials.

### Controlled Recovery Execution

`POST /api/cases/{case_id}/recovery` executes a case's **recorded AI recommendation**
and, for `CREATE_PAYMENT_LINK` / `RETRY`, creates the payment link. The request body
only selects the action (`{"action_type": "RETRY", "reason": "..."}`, both optional):

- The **amount** always comes from the database transaction record, and the
  **confidence / recovery probability** always come from the recorded diagnosis.
  A caller cannot supply either, so it cannot step over `MINIMUM_AI_CONFIDENCE` or
  choose what will be charged.
- The **Policy Engine authorizes the action before any provider call**. A `BLOCKED` or
  `ESCALATED` decision returns **403** (with the full decision) and creates nothing.
  `RECOVERED` / `CLOSED` cases return **409** — a settled case is never acted on again.
- The link carries the case on **both** `reference_id` and `notes.case_id`, so a webhook
  can always be traced back to the right case.
- The response and the audit trail state how the link was created:
  `execution_mode: "RAZORPAY_TEST_MODE"` (a real Test Mode object) or
  `execution_mode: "MOCK"` (no provider call was made and the placeholder link —
  `https://mock.invalid/...` — cannot be paid). Mock execution is never labelled or
  recorded as a payment.
- Partial or unrecognised credentials are **not** silently mocked: the request is
  refused with **503** and `error.code: "PAYMENT_UNCONFIGURED"`, the message names the
  variable to fix (or says to unset both to run in `MOCK`), and no link — mock or
  real — is created. Only "no credentials at all" gives mock links.
- Complete Test Mode credentials with no usable provider client (the `razorpay`
  package is not installed, or client construction fails) are refused the same way:
  **503** with `error.code: "PAYMENT_PROVIDER_UNAVAILABLE"`. A deployment that reports
  `TEST_MODE` never hands back a mock link; the message names the missing piece.
- Agent tools cannot create links: the `agent_tools.create_payment_link` tool refuses
  (`POLICY_AUTHORIZATION_REQUIRED`, no link) because links exist only after the Policy
  Engine authorizes the stored recommendation. It used to return a `mock.invalid`
  placeholder, which could be mistaken for recovery activity.
- No secrets are returned; the API returns only the link, its id, amount, mode,
  provider status and the policy decision.

The case is only marked `RECOVERED` by a verified payment webhook.

### Human Review of Escalated Cases

A case the Policy Engine refuses to authorize autonomously becomes `ESCALATED`, and
`HUMAN_REVIEW_REQUIRED` then blocks every further action on it. Only a named reviewer
can resolve it, through `POST /api/cases/{case_id}/review`:

```json
{ "reviewer": "Asha Reviewer", "decision": "APPROVE", "note": "Verified by phone" }
```

| Decision | Effect |
|---|---|
| `APPROVE` | Executes the **recorded** AI recommendation on the reviewer's authority |
| `OVERRIDE` | Executes a **different** executable action (`action_type` required); a note of at least 5 characters is required |
| `CLOSE` | `CLOSED` without recovering anything |
| `MARK_UNRECOVERABLE` | `CLOSED` as uncollectable; a reason is required |

- **Approval is not a bypass.** The Policy Engine is re-run with the reviewer named as
the authorizing human (`evaluate_action(..., authorized_by=...)`). The *autonomy*
thresholds that caused the escalation — `AUTONOMOUS_AMOUNT_LIMIT`,
`MINIMUM_AI_CONFIDENCE`, `MINIMUM_RECOVERY_PROBABILITY` — are recorded as overridden by
that reviewer. Hard stops still refuse: a settled case, an expired case, and an
exhausted retry / reminder / attempt budget return **409**, the case stays `ESCALATED`,
and the refusal is recorded against the reviewer.
- Every decision, including a refusal, writes a **`HUMAN_REVIEW_COMPLETED`** audit
event whose `actor` is the reviewer, with the overridden rule names in its metadata.
- The request can never carry the amount (always the failed transaction) or the
confidence / recovery probability (always the recorded diagnosis).
- A `RECOVERED` case is never closed, and a non-escalated case cannot be approved.
- `GET /api/reviews/queue` lists what is waiting, with the policy rule that escalated
each case (taken from the recorded escalation event, never re-derived).

The reviewer UI is the **Human Review** panel on the case page, reachable from the
**Human review queue** card on the Cases page.

### Webhook Events Handled

- `payment.captured` / `payment_link.paid` → **settles** the case (status `RECOVERED`,
  `recovered_amount` booked) — only when the captured amount equals the amount due
- `payment.failed` / `payment_link.expired` → failure: the case is reopened for the next
  attempt, unless it is already settled (then the event is recorded and ignored)
- `payment.authorized` → recorded, **not** settled: an authorization is not a capture,
  so it must not book revenue that may never arrive
- Unknown events → Logged and acknowledged

### Webhook Safety

- **Signature:** HMAC-SHA256 over the raw body, compared with the raw body, failing
  closed. With no `RAZORPAY_WEBHOOK_SECRET` configured every delivery is rejected (401)
  rather than trusted.
- **Idempotency (durable):** every handled delivery is recorded by its provider event id
  in the `webhook_events` table. A redelivery — also after a restart or on another
  worker, where an in-memory cache would forget — is answered as a duplicate and applies
  nothing twice, so recovered revenue is never double-counted.
- **Ordering:** a delivery is recorded only *after* it has been handled, so a failed
  delivery stays retryable; late or duplicate events for a settled case are recorded and
  ignored instead of reopening or corrupting it.
- **Amount:** a capture that is non-positive or different from the amount due is refused
  with a `PAYMENT_SUCCESS_AMOUNT_UNVERIFIED` / `PAYMENT_SUCCESS_AMOUNT_MISMATCH` audit
  event, and the case is left for manual reconciliation.

| Variable | Where it comes from |
|----------|---------------------|
| `RAZORPAY_KEY_ID` | Razorpay Dashboard → Account & Settings → **API Keys** → *Generate Test Key* (Test Mode toggle on). Starts with `rzp_test_` |
| `RAZORPAY_KEY_SECRET` | Shown once, next to the Test Key ID. Copy it immediately |
| `RAZORPAY_WEBHOOK_SECRET` | Razorpay Dashboard → Account & Settings → **Webhooks** → *Add New Webhook*: URL = `https://<your-public-host>/api/webhooks/razorpay`, secret = a value you choose. Subscribe to `payment.captured`, `payment_link.paid`, `payment.failed`, `payment_link.expired` |

Razorpay only delivers webhooks to a public HTTPS URL. For a demonstration either

- deploy the backend (Render is already configured in `render.yaml`) and point the
  webhook at `https://<service>.onrender.com/api/webhooks/razorpay`, or
- expose the local API through an HTTPS tunnel, e.g.
  `ngrok http 8000` and use the `https://<id>.ngrok-free.app/api/webhooks/razorpay`
  URL it prints. The tunnel URL changes when it restarts, so update the webhook URL
  in the dashboard when it does.

### One Test Mode Payment, End to End

1. Put the three values above in `backend/.env`, then restart the backend so the
   settings are re-read.
2. Confirm they are loaded: `GET /api/config/status` must report
   `"mode": "TEST_MODE"` and `"webhook_configured": true` (the Dashboard banner
   turns from amber `MOCK` to blue `TEST MODE`), and check the startup log line
   `Razorpay client initialized (Test Mode)`. A live (`rzp_live_…`) key is refused
   instead: the endpoint then reports `"mode": "LIVE_REJECTED"`, the startup log
   says so, and no payment link can be created.
3. Start the public endpoint (deploy, or `ngrok http 8000`) and set that URL as the
   webhook in the Razorpay dashboard, with the same secret as
   `RAZORPAY_WEBHOOK_SECRET`.
4. Create or pick a case and diagnose it: `POST /api/agent/diagnose` with
   `{"case_id": "<CASE-ID>"}` (or open the case page and use *Execute recovery
   action*).
5. Execute the recommendation: `POST /api/cases/<CASE-ID>/recovery` with `{}`, or the
   button on the case detail page. The response must say
   `"execution_mode": "RAZORPAY_TEST_MODE"`; `MOCK` means no credentials are
   configured and no real link exists. With partial credentials the call is refused
   with `PAYMENT_UNCONFIGURED` instead — no link is created at all.
6. Open the returned `payment_link` and pay with a Razorpay **test instrument** (for
   example a test card, or UPI `success@razorpay`). No real money moves.
7. Watch the case: within a few seconds the webhook settles it — status `RECOVERED`,
   `recovered_amount` equal to the case amount, a `PAYMENT_SUCCESS` audit event from
   actor `webhook`, and one `webhook_events` row for the delivery.
8. Verify the single booking: re-send the same webhook (Razorpay's *Resend* button, or
   replay the delivery) and confirm the response says `Duplicate event ignored` and the
   case's `recovered_amount` is unchanged.

Until steps 1–3 are done the flow can only be exercised in `MOCK` mode (or by
simulating a signed delivery locally); the real provider round trip is unverified.

## Simulation

The simulation engine runs synthetic transactions through the complete pipeline, producing a realistic mix of outcomes.

### Running a Simulation

```bash
curl -X POST http://localhost:8000/api/simulation/run \
  -H "Content-Type: application/json" \
  -d '{"num_transactions": 100, "seed": 42}'
```

### Simulation Output

```json
{
  "simulation_id": "SIM-XXXXXXXXXXXX",
  "status": "COMPLETED",
  "label": "SIMULATED",
  "num_transactions_processed": 100,
  "revenue_at_risk": 123456.78,
  "simulated_revenue_recovered": 7664.39,
  "recovery_rate": 4.9,
  "processing_duration_seconds": 5.23,
  "metrics": { ... },
  "ml_prediction_stats": { ... }
}
```

### Expected Outcomes

Each simulation produces a realistic distribution of outcomes based on ML predictions, policy rules, and simulated recovery probabilities:

| Outcome | Typical Range | Description |
|---------|--------------|-------------|
| RECOVERED | 5–15% | Cases where policy approved and simulated recovery succeeded |
| OPEN | 10–20% | Cases where recovery failed but more attempts are allowed |
| ESCALATED | 65–85% | Cases blocked by policy (low confidence, high amount, or threshold exceeded) |

> **Note:** Recovery rates vary based on transaction characteristics, ML predictions, and policy configuration. The simulation is deterministic given the same random seed.

**All simulation output is labeled `SIMULATED`.** It is not real customer revenue.

## Business Metrics

Two recovery rates are reported and they are **not** interchangeable:

Three money categories are reported and they are **never** added together into a headline:

| Metric | Formula | Meaning |
|--------|---------|---------|
| Case value (fixed denominator) | SUM(amount) over **all** cases | Never moves as statuses change |
| **Verified Recovered** (`verified_recovered_amount`, headline `total_recovered`) | SUM(recovered_amount) for cases settled by a signature-verified Razorpay webhook | The only money reported as recovered revenue |
| Simulated (`simulated_recovered_amount`) | SUM(recovered_amount) for `SIM-CASE-*` cases / settling events carrying a simulation id | Simulation bookkeeping. Excluded from every headline; historical rows are left intact |
| Unattributed (`unattributed_recovered_amount`) | SUM(recovered_amount) for settled cases with no settling audit evidence | A data problem, shown rather than counted as verified |
| All booked sources (`total_recovered_all_sources`) | verified + simulated + unattributed | Reconciliation figure only |
| **Money Recovery Rate** (headline) | Verified Recovered / Case value × 100 | How much verified money came back |
| All-sources rate (`money_recovery_rate_all_sources`) | All booked money / Case value × 100 | Explicitly labelled, never the headline |
| **Count Recovery Rate** (secondary) | COUNT(status = RECOVERED) / COUNT(cases) × 100 | How many problems were closed |
| Outstanding | Case value − all booked recovered | Money still to chase |
| **Predicted recovery value** (`predicted_recovery_value`) | Σ case.amount × case.recovery_probability over unsettled cases with a stored ML probability | An **estimate**, not revenue and not a forecast of booked money |
| Recovered (7d) / New at risk (7d) | **Verified** settled money / value of cases **created** in the window, unsettled | With deltas vs the previous 7 days (`null` when that period was empty). `simulated_recovered_7d` and `unattributed_recovered_7d` are reported beside it |
| Recovered provenance | `verified` (signature-verified webhook) · `simulated` · `unattributed` | Source of every booked rupee |
| Escalated Cases | COUNT(status = ESCALATED) | |
| Policy Blocked | COUNT(execution_status = BLOCKED_BY_POLICY) | |

Implementation: `backend/app/services/metrics_service.py` (`get_revenue_metrics`), merged into
`GET /api/dashboard/stats`. `total_at_risk` and `recovery_rate` are still returned with their old
meaning so existing callers keep working. Every response carries a `metric_definitions` object
stating what each figure means, and the dashboard/analytics views label verified, simulated and
predicted money separately (`GET /api/dashboard/charts/daily-recovered` returns `amount` for
verified plus `simulated_amount` and `unattributed_amount` per day).

## Limitations

1. **LLM is mocked** — Uses deterministic rules instead of real LLM API
2. **No real provider round trip has been executed yet** — the controlled recovery flow
   and webhook handling are implemented and verified with a stubbed provider (and a
   locally signed webhook); creating a real Test Mode payment link and receiving a real
   Razorpay webhook delivery requires Test Mode credentials and a public HTTPS URL
3. **Recovery execution has no authentication** — consistent with the rest of this MVP
   (single tenant, no user accounts), but `POST /api/cases/{case_id}/recovery` is a
   mutation endpoint: in a deployed demonstration it should sit behind authentication,
   and it must never run with Live Mode credentials
4. **Single-tenant** — No merchant authentication/authorization
5. **No real-time updates** — Dashboard requires manual refresh
6. **SQLite for tests** — Production uses PostgreSQL
7. **No action-specific recovery probabilities** — the ML model predicts a case-level
   probability of recovery, so value scoring cannot rank actions by likelihood; with one
   shared probability and no costs configured, ranking is driven by cost and eligibility
8. **No measured intervention costs** — net recovery is only computed when a deployment
   configures `INTERVENTION_COSTS`; otherwise it is reported as not computed

## Operational Security & Backup

### Demonstration authentication

Mutating endpoints (`agent/diagnose`, `cases/{id}/recovery`, `cases/{id}/review`,
`policies`, `simulation/run`) require a shared secret bearer token:

- Provide it in `backend/.env` as ``DEMO_API_KEY`` (the backend reads `.env`
  automatically).
- Callers send it as ``X-API-Key: <DEMO_API_KEY>``.
- Missing or invalid key -> HTTP 401. Missing/unset key -> HTTP 503 on protected
  routes.
- Webhook deliveries (`/api/webhooks/razorpay`) are **not** key-authenticated;
  they rely on their own HMAC-SHA256 signature, which fails closed.
- The key never leaves the server: it is never logged, never stored in an
  audit event, and never returned to a client. Audit records record the fixed
  identity `demo_api_key`.

To use it from the UI, the same value must be present in both files:

```bash
# backend/.env
DEMO_API_KEY=<generated-value>

# frontend/.env.local  (compiled into the browser bundle - NOT a secret)
VITE_DEMO_API_KEY=<generated-value>
```

**Important:** this is a single-shared-secret demo mechanism, not a security
boundary. The key ships in the browser bundle when the frontend reads it from a
Vite `.env.local` file, so anyone with page source can extract it.

### Rate limiting

Sensitive routes are throttled in memory:

| Route | Limit |
|-------|-------|
| `agent/diagnose` | 10 requests / 60s |
| `cases/{id}/recovery` | 10 requests / 60s |
| `cases/{id}/review` | 10 requests / 60s |
| `policies` | 10 requests / 60s |
| `policies/evaluate` | 10 requests / 60s |
| `simulation/run` | 10 requests / 60s |

The webhook route is exempt so provider retries can never be throttled into a
missed settlement. **Limitation:** in-memory counters vanish on restart and count
per-process, not per-host. For a single-instance demonstration this is sufficient;
production deployments should mount a shared store (e.g. Redis).

### Policy-change audit

Every successful `PUT /api/policies` writes a `POLICY_CONFIG_CHANGED` audit event
recording the authenticated actor (`demo_api_key`), the previous values, the new
values, the changed fields and the timestamp. The configuration write and its
audit event commit in **one** transaction, so a failed change leaves neither
behind. Policy events are not attached to a case, so `audit_events.case_id` is
nullable (Alembic revision `d4a7c1e9b3f2`).

### PostgreSQL backup and restore

The database is PostgreSQL; the schema is managed by Alembic migrations under
`backend/alembic/versions/`. To keep a safe, recent backup for restore:

Always dump **before** running a migration. `pg_dump` needs `-d <dbname>`:
without it, PostgreSQL dumps the `postgres` maintenance database instead and
produces a near-empty archive (a few KB), which is the usual silent backup
failure.

```bash
# 1) Dump the live database to a custom-format archive
pg_dump -h <host> -U <user> -d revenue_recovery -F c -f backup_$(date +%F_%H%M%S).dump

# 2) Prove the archive is real: it must list the application tables and
#    a TABLE DATA entry for each. A tiny file or a "dbname: postgres" header
#    means the dump is useless.
pg_restore -l backup_2026-11-09_230000.dump | head -5   # dbname: revenue_recovery
pg_restore -l backup_2026-11-09_230000.dump | grep -c 'TABLE DATA'   # expect 9

# 3) Restore into a throwaway database for verification
createdb -h <host> -U <user> restore_test
pg_restore -h <host> -U <user> --no-owner --no-privileges \
    -d restore_test backup_2026-11-09_230000.dump

# 4) Compare the copy against the live database (table names are plural)
psql -h <host> -U <user> -d restore_test -c "
  SELECT 'customers', count(*) FROM customers
  UNION ALL SELECT 'transactions', count(*) FROM transactions
  UNION ALL SELECT 'revenue_risk_cases', count(*) FROM revenue_risk_cases
  UNION ALL SELECT 'audit_events', count(*) FROM audit_events;";
```

Notes:

- Create the restore target as a **new empty** database (`createdb restore_test`).
  Do not use `createdb -T revenue_recovery`: PostgreSQL refuses to use a live
  database as a template while it has connections, and restoring into it would
  overwrite the original.
- Use `--no-owner --no-privileges` so the restore does not depend on the same
  roles existing on the target server.
- A dump contains customer data. Keep it out of the repository (`.gitignore`
  excludes `*.dump`) and off shared drives, and encrypt or delete it once the
  verification is done.
- The `.env` file is git-ignored and contains `DATABASE_URL`, which embeds the
  role/password. Never commit it, never paste it into chat or screenshots, and
  rotate the database password periodically.
- Migrations are applied with `cd backend && alembic upgrade head`. To roll back
  one step: `alembic downgrade -1` (only on a copy of the data).
- Verify a restore by comparing row counts of the key tables (`customers`,
  `transactions`, `revenue_risk_cases`, `audit_events`) and the sums of
  `revenue_risk_cases.amount` / `recovered_amount` against the live database
  before pointing the application at the restored instance. Because the dump
  includes `alembic_version`, the restored copy reports the same revision it was
  taken at; run `alembic upgrade head` on it if it should match a newer schema.

### Key hygiene checklist

- [ ] `DEMO_API_KEY` set in `backend/.env` for any demo that needs mutating reads.
- [ ] Never commit `backend/.env`, `*.db`, `*.dump`, or any credential file.
- [ ] Rotate the database password periodically and do not share it in logs.
- [ ] Keep `RAZORPAY_WEBHOOK_SECRET` private; it is the only key that *must* be
       known to both this server and Razorpay's webhook endpoint.
- [ ] Confirm the dashboard banner shows `MOCK` (no key) or `TEST MODE`
       (credentials + webhook secret configured) before any payment claim.
